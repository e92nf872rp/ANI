## Design Decisions

### D-1: async bridge 用 threading.local per-thread event loop

**Ambiguity:** gRPC Python 的 servicer 方法运行在 ThreadPoolExecutor 工作线程中，需要调用 async repository/client。SPEC 未指定桥接方式。

**Choice:** 用 `threading.local()` 为每个工作线程绑定专用 event loop，通过 `_run_async(coro)` 桥接。loop 在线程生命周期内复用。

**Rationale:** 相比 `asyncio.run()`（每次创建+销毁 loop），per-thread loop 避免反复创建/关闭的开销，且规避了 `asyncio.run()` 在已有运行 loop 的线程中的边界问题。gRPC ThreadPoolExecutor 线程长生命周期复用，per-thread loop 是最高效的桥接方式。

### D-2: rag-engine client 用 REST 传输 + gRPC-intent 接口

**Ambiguity:** SPEC §2.1 指定 kb-service 通过 gRPC 调 rag-engine Query，但当前 rag-engine 只有 REST endpoint（`POST /api/v1/kb/{kb_id}/query`），无 `rag.proto` 或 gRPC server。

**Choice:** 实现 gRPC 风格接口（`async query(...)` 返回 QueryResponse-shaped dict），传输层用 httpx REST 调 rag-engine REST endpoint。代码注释明确标注 gRPC-intent，待 rag.proto 落地后切换传输层到 grpc.aio 无需改 call site。

**Rationale:** 功能上满足 AC3（Query 调用），不因等待 proto 而阻塞 Issue #007。接口稳定，未来升级为真正 gRPC 只需替换 client 内部传输。

### D-3: CoreClient 注入式 client 支持 header 合并

**Ambiguity:** 测试需注入 httpx.MockTransport client，但 CoreClient 的 tenant header 在构造时设置。

**Choice:** CoreClient 构造时，若传入外部 client（用于 MockTransport），则 `client.headers.update(headers)` 合并 tenant header 到注入的 client 上。

**Rationale:** 测试无需手动设置 header，生产路径（自建 client）行为不变。

### D-4: document soft_delete 用 parse_status='failed' + error_message='deleted'

**Ambiguity:** SPEC §6.1 DeleteDocument 算法写 `SET parse_status='deleted'`，但 init schema CHECK 约束只允许 `pending|parsing|indexing|ready|failed`，无 `deleted` 值。

**Choice:** 软删时设 `parse_status='failed', error_message='deleted'`，不新增 enum 值（避免迁移）。

**Rationale:** 保留行用于审计，从 ready/parse 列表排除。新增 enum 值需 ALTER TABLE 迁移，超出 Issue #007 scope（数据访问层）。

## Deviations

### DV-1: NotifyDocumentUploaded 未实现同事务 outbox + Core HEAD checksum

**Spec:** SPEC §6.1 NotifyDocumentUploaded 要求：校验 idempotency_key → Core HEAD object 验证 checksum → 同事务写 async_tasks + outbox_events → 返回 AsyncTaskRef。

**Implementation:** 当前仅校验 idempotency_key + update parse_status='pending'，返回合成 AsyncTaskRef。Core HEAD checksum 验证、同事务 outbox 写入、NATS dispatch 均留 TODO(US-010)。

**Reason:** outbox dispatcher + NATS 发布属 US-010 批次 scope。Issue #007 AC 仅要求 repositories + client 实现，不要求 NotifyDocumentUploaded 完整业务逻辑。标注 TODO 确保后续批次补齐。

### DV-2: Query 未实现 kb_messages 持久化 + Redis session cache

**Spec:** SPEC §6.1 Query 算法要求 INSERT kb_messages(user) + Redis RPUSH + 调 rag-engine + INSERT kb_messages(assistant) + Redis LTRIM。

**Implementation:** 当前仅校验 idempotency_key + 调 rag-engine client 返回结果。kb_messages 持久化 + Redis session cache 留 TODO(US-010)。

**Reason:** Redis session cache + message 持久化属 US-010 批次 scope。Issue #007 AC 聚焦数据访问层 + client 实现，Query wiring 的最小可用路径（调通 rag-engine）已满足 AC3。

### DV-3: CreateKB embedding dimension 硬编码 1024

**Spec:** SPEC §6.1 step 4 `dim: <embedding_dim>`，应从 embedding_model 推导。

**Implementation:** 硬编码 `dim = 1024`（bge-m3 的维度）。

**Reason:** 当前仅支持 bge-m3 一个 embedding model，1024 是其固定维度。未来支持多 model 时需建 model→dim 映射表，属后续批次。

## Tradeoffs

### T-1: CreateKB 跨 DB + Core API 非原子性（TOCTOU）

**Alternatives:**
- **A（当前）:** 先 INSERT knowledge_bases，再调 Core POST /vector-stores，最后写 async_tasks。三步非原子。
- **B:** 先写 async_tasks(pending) 占位，调 Core，成功后 INSERT knowledge_bases + complete_task。利用 UNIQUE idempotency_key 兜底并发。
- **C:** 用 outbox pattern 把 Core 调用转为事件驱动，最终一致。

**Pros/Cons:**
- A：简单、直白、符合 SPEC §6.1 顺序；并发时 Core 可能创建孤儿 vector-store。
- B：并发安全更好；但偏离 SPEC 顺序，且 Core 失败时需清理 async_tasks。
- C：最稳健；但需 outbox dispatcher（US-010），超出 Issue #007 scope。

**Chosen:** A（当前）。SPEC §6.1 CreateKB 算法未要求单事务跨 Core API；`async_tasks.idempotency_key` UNIQUE 约束提供最终保障；完整并发安全属 US-010 outbox 批次范畴。失败时 best-effort soft_delete KB 行。

### T-2: repository 每方法独立事务 vs 外部事务管理

**Alternatives:**
- **A（当前）:** 每个 repository 方法内部 `async with conn.transaction()` 开启自己的事务。
- **B:** repository 方法不开启事务，由调用方（grpc_server）管理事务边界。

**Pros/Cons:**
- A：repository 自洽、易测试、RLS context 自动清理；但无法跨多个 repository 调用共享一个事务。
- B：支持跨 repository 原子事务（如 NotifyDocumentUploaded 同事务写 document + async_task + outbox）；但调用方需手动管理 RLS context。

**Chosen:** A（当前）。Issue #007 的 repository 是独立 CRUD，无跨 repository 原子需求。NotifyDocumentUploaded 的同事务需求（US-010）届时可增加 `*_in_tx` 变体方法或在外部事务中调用 outbox.insert_event（后者已设计为不自行开事务）。

## Open Questions

### OQ-1: rag.proto 何时落地

当前 rag-engine client 用 REST 传输。SPEC §2.1 指定 gRPC。需确认：rag.proto 由哪个批次定义？US-010 还是独立批次？落地后需将 RagEngineClient 传输层从 httpx 切换到 grpc.aio。

### OQ-2: CreateKB 并发安全是否需在 US-010 补齐

当前 CreateKB 的 TOCTOU 窗口在并发相同 idempotency_key 时可能创建孤儿 Core vector-store。需确认：US-010 outbox dispatcher 是否覆盖此场景，或需独立修复（方案 B/C）。

### OQ-3: `make test` PowerShell 兼容性

Makefile `test-go` 规则用 `GOCACHE=... go test` Unix 内联环境变量语法，PowerShell 解释为命令导致失败。此为 pre-existing 平台问题（Makefile 未被本批次修改）。需确认：CI 环境是否用 Unix shell（则无此问题），或需为 Windows 开发者增加 PowerShell 兼容的 Makefile target。

### OQ-4: embedding_model → dimension 映射

CreateKB 硬编码 dim=1024（bge-m3）。需确认：未来支持多 embedding model 时，model→dim 映射放在 kb-service config 还是 Core 端。
