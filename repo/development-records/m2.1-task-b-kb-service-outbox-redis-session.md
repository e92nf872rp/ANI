## Design Decisions

### D1: NotifyDocumentUploaded 用确定性 idempotency_key 而非 proto 字段

**Ambiguity:** SPEC §6.4 要求幂等重放，但 `NotifyDocumentUploadedRequest` proto 没有 `idempotency_key` 字段（proto 是 source of truth）。

**Choice:** 合成确定性 key `kb.parse:{tenant_id}:{kb_id}:{doc_id}`，用于 `async_tasks.idempotency_key` 查重。重试时返回相同 `AsyncTaskRef`。

**Rationale:** proto 不携带 key，只能从请求三元组派生；确定性保证重试得到相同 task_id。未做 Core HEAD 校验和检查（proto 无 `checksum_sha256` 字段）。

### D2: dispatcher 用 publish-all-then-batch-mark 而非 per-event mark

**Ambiguity:** SPEC §6.1 dispatcher 算法描述 `for r in rows: nats.publish; UPDATE published=TRUE`，未指定是否批量。

**Choice:** 先 publish 全部事件到 NATS，再用单个 `UPDATE ... WHERE id = ANY($1::int[])` 批量标记，复用单个连接。

**Rationale:** 原逐事件 `pool.acquire()` 在 100/批次下产生 100 次连接获取（pool max_size=10，与 gRPC servicer 共享），高负载下序列化。批量标记将 100 次连接获取降为 2 次（list + batch mark）。at-least-once 语义不变：publish 与 mark 间崩溃 → 下次重新发布，rag-engine 必须按 doc_id 幂等（模块 docstring 已声明）。

### D3: SessionCache best-effort 降级，不 gate Query 成功

**Ambiguity:** SPEC §7.3 说 Redis 降级为 DB-only，但未说 Query 是否应失败。

**Choice:** `SessionCache.append_message` 捕获所有 Redis 错误并 log warning，不抛给调用方。`_default_session_cache` 在 Redis 不可用时返回 `None`，`_query` 检测 `None` 跳过缓存。

**Rationale:** 缓存是性能层，不是正确性层；`kb_messages` DB 持久化已保证数据不丢。降级到 DB-only 比让 Query 失败更符合 §7.3。

### D4: Query 中 user 消息写入用单事务，assistant 消息独立事务

**Ambiguity:** SPEC §6.1 Query 算法未明确事务边界。

**Choice:** `create_session_in_tx` + `insert_message(user)` 在一个 `conn.transaction()` 内；assistant `insert_message` 在另一个独立事务（因中间隔着 rag-engine 网络调用，不能跨网络调用持事务）。

**Rationale:** 跨 rag-engine 网络调用不能持 DB 事务（长事务 + 网络不可控）。但 user 消息的两步写入应原子（避免 session 行存在但无 user message）。

## Deviations

### DV1: `create_session` 改用 `ON CONFLICT (id) DO NOTHING`（SPEC 未指定）

**Spec:** SPEC §6.1 Query step 2 只说 "resolve session_id (empty → new UUID)"，未说 session 行如何插入。

**Implementation:** `create_session` 用 `INSERT ... ON CONFLICT (id) DO NOTHING RETURNING id`，冲突时返回已有 session_id。

**Why:** 多轮 Query 复用同一 `session_id` 时，原 `INSERT` 会产生重复 `kb_sessions` 行，污染 `ListKBSessions`（P1 RPC）结果。`kb_sessions.id` 是 PK（migration 确认），`ON CONFLICT` 安全。

### DV2: dispatcher 增加指数退避与日志去重（SPEC §6.1 未要求）

**Spec:** SPEC §6.1 dispatcher 算法是 `loop: dispatch; sleep(1s)`，无退避策略。

**Implementation:** 连续失败时 backoff = `min(poll_interval * 2**min(n-1,8), 30s)`，且每个退避窗口最多记一条 traceback。

**Why:** 持续 DB/NATS 故障下原算法每秒刷一条完整 traceback，日志洪泛。SPEC §7.3 只要求"降级为延迟派发"，退避不改变 at-least-once 语义，属运维增强。review-it 发现并修复。

### DV3: `_default_session_cache` 回退为每次构造（非 lazy singleton）

**Spec:** 无相关 SPEC 规定。

**Implementation:** 生产路径由 `main.py` lifespan 构建单例并注入 `session_cache_factory`；`_default_session_cache`（仅 skeleton/测试用）每次构造新实例，无模块全局缓存。

**Why:** 曾尝试用模块级 lazy singleton 避免重复构造，但破坏测试隔离（跨测试泄漏状态）。生产路径已不依赖默认函数，保持默认函数简单（每次构造）符合最小复杂度原则。

## Tradeoffs

### T1: `*_in_tx` 变体 vs 单一函数 + 事务参数

**Alternatives:**
- (a) 为每个 repo 函数提供 `*_in_tx` 不开事务变体 + 原函数委托（当前方案）
- (b) 单一函数 + `in_tx: bool` 参数控制是否开事务
- (c) 所有函数都不开事务，由调用者负责

**Chosen:** (a) — `create_task_in_tx` / `update_parse_status_in_tx` / `create_session_in_tx` / `insert_message_in_tx` 不开事务，原函数 `async with conn.transaction(): return await *_in_tx(...)` 委托。

**Why:** (b) 需要每次调用传 `in_tx` 参数，易用错；(c) 让所有调用者负责事务，增加重复代码。(a) 保留原函数自包含（单独调用安全），同时支持外层原子事务。代价是有两套函数，但 SQL 只写一次（委托模式），无重复。

### T2: dispatcher 批量 mark vs 逐事件 mark

**Alternatives:**
- (a) publish-all-then-batch-mark（当前）
- (b) 逐事件 publish + mark（原实现）
- (c) publish-all + 逐事件 mark

**Chosen:** (a)。

**Why:** (b) 100 次连接获取，性能差；(c) 仍 100 次连接获取。(a) 只 2 次连接获取 + 1 次 UPDATE。代价：一个 publish 失败则整批不标记（下次全重发），但 rag-engine 幂等兜底，at-least-once 语义不变。

### T3: SessionCache 用 `redis.asyncio` pipeline vs 多次 await

**Alternatives:**
- (a) `pipeline()` 批量执行 RPUSH+EXPIRE+LTRIM（当前）
- (b) 三次独立 `await`

**Chosen:** (a)。

**Why:** pipeline 单次 round-trip，原子性更好（虽非事务但减少网络往返）。代价：pipeline 不保证原子（中间可被其他命令插入），但 cache 是 best-effort，不强求原子。

## Open Questions

### OQ1: rag-engine parse_worker 是否已实现 doc_id 幂等？

**Assumption:** dispatcher at-least-once 依赖 rag-engine 按 doc_id 幂等。模块 docstring 声明"rag-engine SPEC covers this"。

**Verify:** US-018（端到端异步链路）应验证 rag-engine 收到重复 `kb.parse` 事件时不重复解析。当前批次未覆盖。

### OQ2: dispatcher 退避上限 30s 是否合适？

**Assumption:** 持续故障下 30s 退避平衡了"及时恢复"与"日志噪音"。

**Verify:** 生产环境长期运行后观察 dispatcher 在真实 NATS/DB 抖动下的恢复延迟。若太长可调低 `MAX_BACKOFF_INTERVAL_SECONDS`。

### OQ3: `_build_session_cache` 同步函数在 async lifespan 中调用

**Assumption:** `aioredis.from_url()` 不实际连接（惰性），同步调用安全。

**Verify:** 若 `from_url` 未来版本改为在构造时连接，需改为 `async def _build_session_cache`。当前 `redis-py` 实现是惰性的，文档已注明。

### OQ4: `ON CONFLICT (id) DO NOTHING` 跨 tenant UUID 碰撞

**Assumption:** UUID v4 碰撞概率 ≈ 2^-122，且 `kb_messages.tenant_id` 冗余 RLS 兜底过滤跨 tenant 数据。

**Verify:** 无需修复，但若未来 session_id 来源改为非 UUID（如用户指定），需加 tenant 约束到 `ON CONFLICT` 子句。
