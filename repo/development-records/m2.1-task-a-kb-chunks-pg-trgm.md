## 1. Design Decisions

### D-1：扩展与建表拆分为两个迁移文件

- **歧义：** SPEC §2.4 文件结构已指定 `001_pg_trgm_extension.sql` 与 `002_kb_chunks.sql` 两个文件，但未说明为何不合并。
- **选择：** 按 SPEC 文件结构拆分，001 先建扩展，002 再建表与索引。
- **理由：** (1) 扩展创建需要 superuser/owner 权限，表/索引创建只需要表 owner 权限，在实际部署（CloudNativePG / 托管 PG）中这两步可能由不同角色执行；(2) GIN trgm 索引依赖 pg_trgm 扩展，必须先建扩展；(3) 单独的扩展文件可被其他未来需要 trigram 检索的表复用，避免重复创建。执行顺序由文件名前缀 `001`/`002` 的字典序约定。

### D-2：在 002_kb_chunks.sql 追加 GRANT + RLS（review-it 触发）

- **歧义：** SPEC §3.1 给出的 SQL 块只含 `CREATE TABLE` + `CREATE INDEX` + `CREATE EXTENSION`，未显式包含 GRANT 与 RLS。SPEC §3.4 只提及幂等性，未提 RLS。SPEC §8.1 只说"所有 repository 查询带 `tenant_id = current_tenant_id`（RLS）"。
- **选择：** 在 002 中追加 `GRANT SELECT, INSERT, UPDATE, DELETE ON kb_chunks TO ani_app;` + `ENABLE/FORCE ROW LEVEL SECURITY` + `CREATE POLICY tenant_isolation AS RESTRICTIVE USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid)`。
- **理由：** 仓库既定约定——`repo/deploy/migrations/` 下所有业务表迁移（`20260501000100_init_schema.sql` 对 `kb_documents`/`kb_messages`/`async_tasks`/`outbox_events`，`20260520000500_network_resources.sql` 对 `network_*`，`20260620000100_network_routes.sql` 对 `network_routes`）都强制 GRANT + RLS。SPEC §8.1 明确 RLS 是租户隔离机制，而应用账号 `ani_app_user` 是 non-superuser/non-bypassrls，RLS 必须启用才生效。无 GRANT 则应用账号直接权限拒绝；无 RLS 则跨租户可读，违反 FR-15 与 SPEC §8.1。这是 SPEC 隐含的既有约定，不是新增设计。

## 2. Deviations

### DEV-1：SPEC §3.1 SQL 块未含 RLS/GRANT，实现追加

- **SPEC：** §3.1 的 SQL 示例只含建表 + 索引 + 扩展。
- **实现：** 额外追加 GRANT + RLS policy（见 D-2）。
- **原因：** SPEC §3.1 是 schema 示例而非完整迁移脚本；§8.1 明确 RLS 是强制隔离机制；仓库既有迁移均含 GRANT+RLS。这不与 SPEC 冲突，而是补齐 SPEC 未展开的部署侧细节。review-it 阶段将其识别为 F1 finding 并修复。

### DEV-2：`kb_id`/`doc_id`/`parent_chunk_id` 使用软 FK，不建硬 FK

- **SPEC：** §3.3 明确"`kb_chunks.kb_id` → `knowledge_bases.id`（软 FK，RLS 同租户）"、"`kb_chunks.doc_id` → `kb_documents.id`"、"`kb_chunks.parent_chunk_id` → `kb_chunks.id`（自引用）"，均为软 FK。
- **实现：** 三个字段均为 `UUID`（parent_chunk_id 可空），无 `REFERENCES`。
- **对比：** 既有 `kb_documents` 在 `20260501000100_init_schema.sql` L306 使用 `kb_id UUID NOT NULL REFERENCES knowledge_bases(id) ON DELETE CASCADE`（硬 FK）。
- **原因：** SPEC 对 `kb_chunks` 明确选择软 FK。kb_chunks 由 rag-engine parse_worker 跨服务异步写入，且删除文档时需先清理 Milvus 向量再软删 chunk，硬 FK `ON DELETE CASCADE` 会在异步链路中引入阻塞/死锁，并绕过应用层清理逻辑。软 FK + RLS 是 SPEC 的明确取舍。

## 3. Tradeoffs

### T-1：`parent_content` 冗余存储 vs JOIN 自表

- **可选方案 A：** 只存 `parent_chunk_id`，查询时 JOIN `kb_chunks` 自表取父块内容。
- **可选方案 B（选择）：** 在 child 行冗余存 `parent_content`，查询时直接取本行。
- **取舍：** A 节省存储但每次检索需自 JOIN，pg_trgm 关键词命中 child 后回填父块多一次查询；B 用空间换时间，检索路径单次查询即可拿到 child + parent_content。RAG 检索是高频读路径，父子分块回填是每次 Query 必经，B 更优。存储成本可接受（父块文本远小于向量数据）。
- **依据：** SPEC §3.1 已含 `parent_content TEXT` 字段，本选择与 SPEC 一致。

### T-2：GIN trgm 索引 vs pg_bigm / ZomboDB

- **可选方案 A（选择）：** `pg_trgm` GIN 索引。
- **可选方案 B：** `pg_bigm`（2-gram，对中文/CJK 更友好）。
- **可选方案 C：** ZomboDB（ES 后端）。
- **取舍：** A 是 PostgreSQL contrib 自带，CloudNativePG 默认可用，无额外依赖；PRD FR-7 明确指定 pg_trgm；B 对中文更好但需额外安装扩展，P0 不引入；C 引入 ES 依赖，违反 Karpathy 原则五（无必要不增实体）。A 胜出。中文检索质量在 P0 可接受，后续如需可升级到 pg_bigm。

### T-3：RLS 幂等模式用 `DROP POLICY IF EXISTS` + `CREATE POLICY`

- **可选方案 A：** `DROP POLICY IF EXISTS ... ; CREATE POLICY ...`（选择）。
- **可选方案 B：** `CREATE POLICY ... ;`（不带 DROP）。
- **取舍：** B 在重复执行时会报错（policy 已存在），违反 SPEC §3.4 幂等性。A 是仓库既定模式（见 `20260520000500` L86-89、`20260620000100` L25-27），重复执行时先删后建为 no-op。A 胜出。

## 4. Open Questions

### OQ-1：kb_chunks 是否需要对 `tenant_id` 建 `REFERENCES tenants(id) ON DELETE CASCADE` 硬 FK？

- **假设：** 当前实现未建，与既有 `kb_documents`（L307 `tenant_id UUID NOT NULL` 无 FK）一致，租户隔离由 RLS 保证。
- **待确认：** 若后续需要"删租户级联清 chunk"的语义，需在单独迁移中补硬 FK；但 P0 删租户不在范围内，软 FK + RLS 足够。
- **建议：** 维持现状，除非 SPEC 明确要求硬 FK。

### OQ-2：迁移脚本是否需要在 `repo/services/kb-service/` 目录补 `Makefile`/迁移工具集成？

- **假设：** 当前 `repo/services/kb-service/` 为空骨架（`go.work` 中 `./services/kb-service` 被注释），迁移脚本由部署侧（`deploy/migrations/` 的迁移工具或 CloudNativePG Job）执行。
- **待确认：** US-008（kb-service 骨架）会决定迁移执行方式（atlas / psql / alembic）。本批次只交付 SQL 文件，执行集成归 US-008。
- **建议：** 不在本批次引入迁移工具依赖。

### OQ-3：`content` 字段是否需要长度上限校验？

- **假设：** SPEC §3.1 仅 `TEXT NOT NULL`，无长度约束。rag-engine 切块逻辑保证块大小（PRD §6 chunk_size 默认 512 token）。
- **待确认：** 若需在 DB 层防御超长块，可加 `CHECK (length(content) <= 65535)`；但 P0 信任 rag-engine 切块边界。
- **建议：** 维持现状，不在 DB 层加长度限制，避免与未来切块策略变化冲突。
