## Design Decisions

### D-1: gRPC client 采用非阻塞拨号 + per-call 超时（对齐 auth_client.go 范式）

**Ambiguity:** SPEC §2.2 指定 `kb_grpc_client.go` 为"gRPC client"但未指定拨号策略与超时模型。SPEC §5.1 line 191 注释 `grpc_client.Call(req) // 含超时`、§6.2 line 245 `超时/UNAVAILABLE 不自动重试，返回 503` 暗示需要超时。

**Choice:** `DialKBGRPC` 用 `grpc.NewClient`（非阻塞懒连接，对齐 `auth_client.go:39`）；`kbGRPCClient` 持有 `timeout` 字段，每个 RPC 方法用 `callCtx, cancel := context.WithTimeout(ctx, c.timeout); defer cancel()` 包裹；超时经 `mapGRPCError` 映射为 HTTP 504 `DEADLINE_EXCEEDED`。

**Rationale:** 集群内 mTLS 链路下，启动时 kb-service 可能未就绪——非阻塞拨号让网关立即启动、连接后台懒建立，首个 RPC 触发时由 per-call 超时返回 503/504。这与项目既有 `auth_client.go` 范式一致（`grpc.NewClient` + 每调用 `WithTimeout`），避免引入第二种拨号模式。per-call 超时还防止慢/挂起的 kb-service 无限占用网关请求 goroutine。

### D-2: SSE 路由注册但 body 为空（US-017 延后）

**Ambiguity:** SPEC §4.3 定义 SSE 事件协议，但 rag-engine + vLLM streaming 编排属于 US-017，依赖未就绪。Issue #18 AC 只要求"12 端点就位"。

**Choice:** 注册 `/api/v1/svc/knowledge-bases/{kb_id}/query/stream` 路由，校验 question 参数（1-2000 字符，SPEC §4.3），设置 SSE headers（`Content-Type: text/event-stream` / `Cache-Control: no-cache` / `Connection: keep-alive`），写出终结 `event: done` 事件后关闭流。

**Rationale:** 路由表面完整（满足 12 端点 AC），客户端收到合规 SSE 流而非 stub 200 body，不会挂起等待。实际 rag-engine 检索 + vLLM streaming 透传在 US-017 接入。

### D-3: Core 代理路由复用既有 port/adapter，不新建 core_proxy.go

**Ambiguity:** SPEC §2.2 列出 `core_proxy.go [NEW 或复用]`，明确允许复用。`/api/v1/vector-stores/*` 和 `/api/v1/objects/*` 已由 `vector_store_resources.go` / `storage_resources.go` 通过 `ports.VectorStoreService` / `ports.StorageService` 实现。

**Choice:** 复用既有 Core 代理路由，不新建 `core_proxy.go`。

**Rationale:** 新建反向代理会违反 Karpathy 原则 2/3/5（最小代码、不重复、不臆造），并绕过既有 port/adapter 边界。SPEC "复用" 选项正是为此设计。

## Deviations

### DV-1: 错误码 BAD_REQUEST 而非 INVALID_ARGUMENT

**Spec:** SPEC §5.1 列出 gRPC→HTTP 映射表，`INVALID_ARGUMENT` 对应 code `INVALID_ARGUMENT`。

**Implementation:** `mapGRPCError` 将 `codes.InvalidArgument` 映射为 HTTP 400 + code `BAD_REQUEST`（[kb_grpc_client.go:208-209](file:///c:/Users/PC/Desktop/ANI/repo/services/ani-gateway/internal/router/kb_grpc_client.go#L208-L209)）。

**Why:** 网关层 handler 的输入校验（`idempotency_key` 缺失、`name` 缺失、`question` 超 2000 字符等）已统一用 `BAD_REQUEST` code（`writeDemoError(c, http.StatusBadRequest, "BAD_REQUEST", ...)`）。gRPC 透传的 `InvalidArgument` 与本地校验应返回同一 code，使客户端无需区分错误来源。这是项目网关错误响应的既有约定，非新引入。

### DV-2: 3 个 P1 路由在网关返回 501 而非透传 gRPC UNIMPLEMENTED

**Spec:** SPEC §5.1 暗示 P1 端点应透传 kb-service 返回的 `UNIMPLEMENTED`。

**Implementation:** 当 `client == nil`（kb-service 未配置）时，P1 路由在网关直接返回 501 `NOT_IMPLEMENTED`（[kb_resources.go:307,332,357](file:///c:/Users/PC/Desktop/ANI/repo/services/ani-gateway/internal/router/kb_resources.go#L307-L307)）；当 client 非 nil 时透传 kb-service 的 UNIMPLEMENTED。

**Why:** 本地开发环境 kb-service 未部署（`KB_SERVICE_GRPC_ADDR` 为空），若不返回 501 则路由会 404 或 panic。网关层 501 降级语义与 kb-service UNIMPLEMENTED 一致，客户端行为相同。当 kb-service 部署后，透传路径自然激活。

## Tradeoffs

### T-1: 死代码 GetDocument / NotifyDocumentUploaded 保留

**Alternatives:**
- A) 删除这两个接口方法及实现（遵循 Karpathy 原则 2/5，最小代码）
- B) 保留为 kb-service P1/P2 端点（notify-uploaded/reparse）的预留接口

**Pros/Cons:** A 减少当前死代码但需在对应 Issue 重新添加接口+实现+测试 fake；B 当前有未用代码但接口表面稳定，后续 Issue 直接接 handler。

**Choice:** B（保留）——代码审查时用户明确选择保留，因对应 notify-uploaded/reparse 端点是已知后续 Issue，接口表面已对齐 kb-service proto，保留避免反复增删。

### T-2: GATEWAY_LISTEN_ADDR env 引入

**Alternatives:**
- A) 不引入，端口硬编码 `:8080`（原状）
- B) 引入 `GATEWAY_LISTEN_ADDR` env 覆盖

**Pros/Cons:** A 简单但本地多实例冒烟（已有占用 8080 的进程）需额外手段；B 增加 1 个 env 但运维/冒烟更灵活，默认仍 `:8080` 向后兼容。

**Choice:** B——最小、通用、向后兼容，冒烟测试证明新二进制可启动且路由可命中。

## Open Questions

### OQ-1: kb-service gRPC server 部署后需补 live E2E

本地 live 冒烟验证了 12 路由表面、9 个 P0 端点的 503 降级、3 个 P1 端点的 501、SSE headers+done、Core 代理 200。但 `kb-service` 未部署在 real-k8s-lab 集群（依赖 #6 的部署清单未提供），真实 gRPC 拨号 + RPC 透传链路未在 live 环境验证。待 kb-service 部署并配置 `KB_SERVICE_GRPC_ADDR` 后，需补一次 live E2E（带真实 Bearer token + kb-service 响应）。

### OQ-2: OpenAPI custom_metadata 类型 proto/string vs object 差异

proto `KBDocument.custom_metadata` 为 `string`（JSONB），但 services/v1.yaml OpenAPI schema 定义为 `object`（`additionalProperties: true`）。网关 JSON 映射当前用 string（与 proto 一致）。`validate-services-contract` 未标记此差异。需确认 OpenAPI 是否应在 schema 层面声明 `string` 以对齐 proto，或 kb-service 在序列化时将 JSONB string 解析为 object 返回。
