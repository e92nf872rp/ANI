## 实现摘要

实现 ani-gateway 持有的 SSE 流式问答端点 `GET /api/v1/svc/knowledge-bases/{kb_id}/query/stream`（SPEC §4.3 / US-017）。handler 编排完整 RAG 流程：rag-engine 检索 → prompt 构建 → vLLM `stream=true` 流式生成 → token 透传 → sources 事件 → done 事件。支持四种 SSE 事件类型（token/sources/done/error），流前 400/401/404 返回 JSON，流中错误发送 error 事件后关闭流。客户端断开通过 context cancel 中止 vLLM stream。

经三轮代码审查（issue-019 SSE 代码审查 + 项目框架审查 + review-it closeout），共修复 17 项问题，涵盖类型安全、性能优化、资源泄漏、线程安全、错误处理、配置一致性等方面。

## Design Decisions

### D-1: SSE handler 调用 rag-engine REST 而非 gRPC

**Ambiguity:** SPEC §5.1 描述 SSE handler 调用 rag-engine 检索，但 rag-engine 的 proto（`rag.proto`）不在 `buf.gen` 模块中（位于 `ai/rag-engine/app/grpc/rag.proto`，在 `api/proto` 之外）。

**Choice:** 通过 REST HTTP 调用 rag-engine 的 `POST /api/v1/kb/{kb_id}/query` 端点，而非生成 Go gRPC client。

**Rationale:** 保持 SSE handler 依赖在 gateway 代码边界内，避免跨团队 proto 生成步骤。REST 消息体镜像 `kb_service.proto` QueryRequest/QueryResponse 结构，未来可无缝切换到 gRPC。

### D-2: parseVLLMChunk 只转发 content delta，跳过 reasoning delta

**Ambiguity:** SPEC §4.3 定义 `event: token` 携带 `delta` 字段，但未说明如何处理 Qwen3 模型的 `reasoning`（思维链）delta。

**Choice:** 只转发 `content` delta 作为 token 事件；`reasoning` delta（Qwen3 chain-of-thought）被完全跳过。

**Rationale:** 思维链是模型内部推理过程，不应混入答案文本。如果转发 reasoning token，客户端会看到模型的思考过程而非最终回答，破坏用户体验。

### D-3: score_threshold 默认值设为 0（禁用阈值过滤）

**Ambiguity:** SPEC §5.2 定义 `score_threshold` 参数但未指定 SSE 端点的默认值。系统全局默认为 0.3。

**Choice:** SSE handler 的 `score_threshold` 默认设为 0（禁用过滤）。

**Rationale:** RRF fusion scores 通常在 ~0.016 范围，远低于 0.3 全局默认。如果使用 0.3 默认值，所有 sources 会被过滤掉，sources 事件永远为空数组。默认设为 0 确保 SSE 端点在无显式参数时返回真实检索结果。E2E 测试显式传递 `score_threshold=-1` 进一步确保禁用。

### D-4: vLLM HTTP client 使用无整体超时 + ResponseHeaderTimeout

**Ambiguity:** SPEC §5.1/§5.4 要求"客户端断开 → 取消 vLLM stream"，但未指定 HTTP client 超时模型。

**Choice:** vLLM HTTP client 不设整体 `Timeout`（stream 保持打开），使用 `ResponseHeaderTimeout: 30s`（首字节等待上限）+ `IdleConnTimeout: 90s` + `MaxIdleConnsPerHost: 10`。请求生命周期由 `context` 控制——客户端断开时 context cancel 中止 stream。

**Rationale:** 流式生成可能持续数十秒到数分钟，整体超时会截断有效生成。`ResponseHeaderTimeout` 确保 vLLM 不可达时不无限等待。`IdleConnTimeout` + `MaxIdleConnsPerHost` 管理连接池，防止空闲连接积累。rag-engine 同步 client 使用 `http.Client{Timeout}` 整体超时（30s/可配），因为检索是同步 request-response。

### D-5: Settings.llm 赋值修复 LlamaIndex PromptHelper 上下文窗口问题

**Ambiguity:** SPEC §5.1 指定 `ContextChatEngine.from_defaults(llm=OpenAILike(..., context_window=...))`，但未预见 LlamaIndex `CompactAndRefine` 响应合成器使用 `Settings.prompt_helper`（全局单例）而非传入的 LLM metadata。

**Choice:** 在 `_build_engine` 中显式设置 `Settings.llm = llm`，确保 `PromptHelper` 从 LLM metadata 获取正确的 `context_window`（32768）和 `num_output`（2048）。

**Rationale:** 不设置 `Settings.llm` 时，`Settings.prompt_helper` 回退到 `PromptHelper()` 默认值（`context_window=3900, num_output=256`）。当检索到的 sources 填满 3900 token 窗口后，`chunk_size = available_context // num_chunks - padding` 产生负数，抛出 `"Chunk size -X is not positive"`。这是 LlamaIndex 框架的全局状态设计缺陷，显式赋值是最小侵入性修复。

## Deviations

### DV-1: SSE 响应使用缓冲模式而非逐帧 Flush

**Spec:** SPEC §11.2 记录"缓冲响应模型"为已知风险，建议未来升级到 Hijack-based writer。

**Implementation:** 使用 Hertz 的 `c.Write` 累积到响应缓冲，事件序列 `token*→sources→done` 在 handler 返回时一次性 flush。

**Rationale:** Hertz 的缓冲模型在 P0 阶段是正确的——事件序列格式合规，响应是有效的 `text/event-stream`。逐帧 Flush 需要使用 Hijack API 直接操作底层连接，增加复杂度。SPEC §11.2 已将其标记为未来改进项，不在 issue-019 范围内。

### DV-2: rag-engine REST 端点 500 错误返回通用消息

**Spec:** 原 `query.py` 实现 `except Exception as exc: raise HTTPException(status_code=500, detail=str(exc))`，将内部异常字符串暴露给客户端。

**Implementation:** 改为 `logger.exception("query_kb internal error")` + `raise HTTPException(status_code=500, detail="internal server error")`。

**Rationale:** 原实现可能泄露数据库连接串、文件路径等敏感信息。修改后在服务端日志记录完整异常（带 traceback），客户端只看到通用错误消息。

### DV-3: vLLM_CONTEXT_WINDOW 从 4096 提高到 32768

**Spec:** SPEC §5.1 和 `.env.example` 原默认 `VLLM_CONTEXT_WINDOW=4096`。

**Implementation:** 代码默认值和 `.env.example` 均更新为 32768。

**Rationale:** Qwen3.6-35B-A3B 模型支持 32K+ 上下文窗口。4096 对于 RAG 场景过小——检索到的 sources 会快速填满上下文窗口，触发 PromptHelper 计算 `chunk_size` 为负数。32768 匹配模型实际容量，为 sources + prompt + 生成留出充足空间。

## Tradeoffs

### T-1: REST vs gRPC 调用 rag-engine

**Alternatives:**
1. REST HTTP（选中）—— 现有 rag-engine REST 端点，消息体镜像 proto 结构
2. 生成 Go gRPC client —— 从 `rag.proto` 生成 Go stub

**Pros/Cons:**
- REST: 零额外生成步骤、消息体可直接切换到 gRPC、减少编译依赖
- gRPC: 更强类型安全、避免 JSON 序列化开销、protobuf 二进制更高效

**Winner:** REST — 避免跨团队 proto 生成步骤，消息体已镜像 proto 结构，性能差异在检索阶段可忽略（瓶颈在 vLLM 生成阶段）。

### T-2: bytes.Buffer vs fmt.Sprintf 编码 SSE 帧

**Alternatives:**
1. `bytes.Buffer` + `Grow` + `WriteString`（选中）
2. `fmt.Sprintf("event: %s\ndata: %s\n\n", ...)` + `[]byte(string)`

**Pros/Cons:**
- bytes.Buffer: 两次分配（Buffer + JSON），预分配后零拷贝拼接
- fmt.Sprintf: 三次分配（Sprintf + string→[]byte 转换 + JSON），每次 token 事件都发生

**Winner:** bytes.Buffer — SSE 流每秒可能发送数十个 token 事件，减少每次帧编码的内存分配。`Grow` 预分配精确大小后写入零拷贝。

### T-3: _run_async 错误检测方式

**Alternatives:**
1. `asyncio.get_running_loop()` API 检测（选中）
2. 字符串匹配 `"event loop"` / `"already running"`

**Pros/Cons:**
- API 检测: 跨 Python 版本可靠、不误匹配业务异常消息
- 字符串匹配: 简单但脆弱——业务异常消息含 "event loop" 会被误吞

**Winner:** API 检测 — `asyncio.get_running_loop()` 在无运行循环时抛 `RuntimeError`，可靠区分嵌套循环错误和业务错误。

## Open Questions

### OQ-1: SSE 逐帧 Flush 时机

SSE 响应当前使用缓冲模式，handler 返回时一次性 flush。对于长生成（数百 token），客户端可能等待较长时间才收到第一批 token。**需确认**：P0 阶段是否可接受此延迟？如果前端需要实时逐 token 显示，需在后续 issue 中升级到 Hijack-based writer。

### OQ-2: idempotency_key 在 rag-engine REST 端点的处理

`QueryRequest` 定义了 `idempotency_key` 字段（注释 "prevents duplicate billing on retry"），但 rag-engine REST 端点和 gRPC servicer 均未实现去重逻辑。**需确认**：idempotency 是在 rag-engine 实现还是由 gateway 中间件层处理（gateway 已有 `Idempotency` 中间件，仅对 POST/PUT/PATCH 生效，SSE 端点使用 GET）？

### OQ-3: ChatMemoryBuffer / RedisChatStore 资源生命周期

`QAService` 懒加载 `RedisChatStore`，缓存在 `self._chat_store`，但无关闭逻辑。`main.py` lifespan shutdown 不关闭它。**需确认**：进程退出时 Redis 连接是否需要优雅关闭？当前依赖 OS 清理 TCP 连接 + Redis 服务端超时回收。

### OQ-4: qa_service 预检查与 engine.chat 重复检索

`QAService.chat` 先用 `fusion_retriever.retrieve(question)` 做预检查（score_threshold 短路），再调用 `engine.chat(question)`（内部再次检索）。**需确认**：是否值得为消除重复检索重构为手动检索 + 手动构建 prompt + 直接 LLM 调用（绕过 ContextChatEngine）？这会减少一次检索开销但失去多轮对话上下文管理。
